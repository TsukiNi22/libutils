    CommunicationCommunication

    How the TCP server and client exchange payloads, how the EETP protocol encrypts them, and how processes talk through pipes and the slotted shared memory.Comment le serveur et le client TCP échangent des payloads, comment le protocole EETP les chiffre, et comment les processus communiquent par pipes et par la mémoire partagée à slots.

    Updated 2026-11-26

    Two ways for programs to talk: the network (a TCP Server and Client, optionally encrypted by EETP) and the processes of one machine (pipes, a child process, a shared memory). The classes are on Network, SManip and Encapsulation.

    Deux façons pour des programmes de communiquer : le réseau (un Server et un Client TCP, chiffrés en option par EETP) et les processus d'une même machine (pipes, un processus enfant, une mémoire partagée). Les classes sont sur Network, SManip et Encapsulation.

    1. Payloads over TCPPayloads sur TCP

    A Server and a Client exchange payloads (strings ended by a separator, '\n' by default) through a socket object. listen() reads what is available without blocking, join() waits for the next epoll event; stop() / kill() can be called from another thread. On Windows the sockets use Winsock 2 and the epoll is emulated over WSAPoll.

    The socket splits the stream into payloads and keeps what is not complete yet: a payload longer than the overflow limit (4048 characters without a separator) is an error, a peer that closes the connection is the None exception SocketClosed and the status Down.

    Un Server et un Client échangent des payloads (des chaînes terminées par un séparateur, '\n' par défaut) à travers un objet socket. listen() lit ce qui est disponible sans bloquer, join() attend le prochain événement epoll ; stop() / kill() peuvent être appelés depuis un autre thread. Sous Windows, les sockets utilisent Winsock 2 et l'epoll est émulé sur WSAPoll.

    Le socket découpe le flux en payloads et garde ce qui n'est pas encore complet : un payload plus long que la limite de débordement (4048 caractères sans séparateur) est une erreur, un pair qui ferme la connexion donne l'exception None SocketClosed et le statut Down.

    2. EETPEETP

    EETPParser keeps the keys of each peer: the client sends SYN (its RSA public key, encrypted with the common RSA key of ~/.ssh/common), the server answers SO (a new AES-256 key, encrypted with the client key), then every message is AES-256-GCM encrypted with a new random iv.

    TypeDirectionContent
    SYNclient → serverclient RSA public key (common RSA)
    SOserver → clientAES-256 key (client RSA)
    other↔AES-256-GCM, frame <iv><tag> ETB <content>, Base64 encoded
    EM↔disconnection, never encrypted

    Warning. The framing changed in v3.0.0: both sides must use v3.0.0 or later.

    EETPParser garde les clés de chaque pair : le client envoie SYN (sa clé publique RSA, chiffrée avec la clé RSA commune de ~/.ssh/common), le serveur répond SO (une nouvelle clé AES-256, chiffrée avec la clé du client), puis chaque message est chiffré en AES-256-GCM avec un nouvel iv aléatoire.

    TypeSensContenu
    SYNclient → serveurclé publique RSA du client (RSA commune)
    SOserveur → clientclé AES-256 (RSA du client)
    autre↔AES-256-GCM, trame <iv><tag> ETB <content>, encodée en Base64
    EM↔déconnexion, jamais chiffrée

    Attention. Le tramage a changé en v3.0.0 : les deux côtés doivent utiliser v3.0.0 ou plus récent.

    3. ProcessesProcessus

    Process wraps fork / execvp / waitpid with pipes and fd duplications applied in the child; Poll wraps epoll; SharedObject loads a .so. On Windows: CreateProcess, WSAPoll, LoadLibrary (.dll); there is no fork, so spawn() alone is a FatalException (UndefinedCall) and only the standard fds can be redirected.

    Process enveloppe fork / execvp / waitpid avec des pipes et des duplications de fd appliquées dans l'enfant ; Poll enveloppe epoll ; SharedObject charge un .so. Sous Windows : CreateProcess, WSAPoll, LoadLibrary (.dll) ; il n'y a pas de fork, donc spawn() seul est une FatalException (UndefinedCall) et seuls les fds standard peuvent être redirigés.

    4. Shared memoryMémoire partagée

    SharedMemory passes messages between processes through a POSIX shared memory split in slots. On Windows it is a file mapping with a named event.

    A message is addressed to one reader (Target(limit, ownership)) or to every reader (Target(limit), 0 = all the connected ones). An Id{id, ownership} links the answers of a conversation, join() waits for a message and returns when the memory is closed. The layout of the slots depends on the writers: Compact for one writer, Interleaved* for many writers at the same time (one cache line per slot for InterleavedAligned).

    SharedMemory transmet des messages entre processus à travers une mémoire partagée POSIX découpée en slots. Sous Windows, c'est un file mapping avec un événement nommé.

    Un message est adressé à un lecteur (Target(limit, ownership)) ou à tous les lecteurs (Target(limit), 0 = tous ceux qui sont connectés). Un Id{id, ownership} relie les réponses d'une conversation, join() attend un message et rend la main quand la mémoire est fermée. La disposition des slots dépend des écrivains : Compact pour un seul écrivain, Interleaved* pour plusieurs écrivains en même temps (une ligne de cache par slot pour InterleavedAligned).
