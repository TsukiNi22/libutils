    ErrorsErreurs

    How libutils reports errors: an exception with a type and a code in C++, a return value and a thread local status in C, and the codes generated from JSON.Comment libutils signale les erreurs : une exception avec un type et un code en C++, une valeur de retour et un statut thread local en C, et les codes générés depuis du JSON.

    Updated 2026-11-26

    Every error of libutils is an exception carrying a type and a code, never a return code. The C API turns the same exception into a return value and a status. The classes and the full list of codes are on Exceptions.

    Chaque erreur de libutils est une exception qui porte un type et un code, jamais un code de retour. L'API C transforme la même exception en valeur de retour et en statut. Les classes et la liste complète des codes sont sur Exceptions.

    1. Type and codeType et code

    The type says how serious it is, the code what happened:

    ClassTypeMeaning
    NoneExceptionNonenot an error (ex: help displayed, Exit)
    WarningExceptionWarningthe program can continue
    ErrorExceptionErrorerror of the call
    CustomExceptiongivena combination of types
    FatalExceptionFatalprints and calls std::abort() from its constructor

    A code can restrict the types it accepts: a forbidden combination ends with FatalException(ExceptionCodeRestriction). Many methods take failsafe (warn instead of throwing) or safe_mode (lock).

    try {
    server.start();
} catch (const utils::exception::IException& e) {
    if (e.getCode() == utils::exception::InternalCode::AlreadyRunning) return;
    std::cerr << e.formated() << std::endl; // [Error] file:line (origin) -> message / function = info
}

    Le type dit la gravité, le code ce qui s'est passé :

    ClasseTypeSignification
    NoneExceptionNonepas une erreur (ex : aide affichée, Exit)
    WarningExceptionWarningle programme peut continuer
    ErrorExceptionErrorerreur de l'appel
    CustomExceptiondonnéune combinaison de types
    FatalExceptionFatalaffiche et appelle std::abort() depuis son constructeur

    Un code peut restreindre les types qu'il accepte : une combinaison interdite finit en FatalException(ExceptionCodeRestriction). Beaucoup de méthodes prennent failsafe (avertir au lieu de lever une exception) ou safe_mode (verrou).

    try {
    server.start();
} catch (const utils::exception::IException& e) {
    if (e.getCode() == utils::exception::InternalCode::AlreadyRunning) return;
    std::cerr << e.formated() << std::endl; // [Error] file:line (origin) -> message / function = info
}

    2. Where the codes come fromD'où viennent les codes

    The codes are generated at the build from cmake/config/exceptions/**/*.json (generated_internal_exception_header.hpp): InternalCode for the library. A project adds its own codes, ExternalCode, with the same JSON format and the same generator (Custom exception codes). The generator refuses a code that isn't a C++ identifier, Undefined or a duplicate.

    OriginC++C (utils_exception.origin)
    a code of libutilsInternalCodeC_API_EXCEPTION_ORIGIN_INTERNAL
    a code of your projectExternalCodeC_API_EXCEPTION_ORIGIN_EXTERNAL
    a standard exceptionstd::exceptionC_API_EXCEPTION_ORIGIN_STD (code C_API_OTHER_EXCEPTION_CODE)
    anything else thrown-C_API_EXCEPTION_ORIGIN_UNKNOWN
    a C function (utils_fail)-C_API_EXCEPTION_ORIGIN_C

    Les codes sont générés au build depuis cmake/config/exceptions/**/*.json (generated_internal_exception_header.hpp) : InternalCode pour la bibliothèque. Un projet ajoute ses propres codes, ExternalCode, avec le même format JSON et le même générateur (Codes d'exception personnalisés). Le générateur refuse un code qui n'est pas un identifiant C++, Undefined ou un doublon.

    OrigineC++C (utils_exception.origin)
    un code de libutilsInternalCodeC_API_EXCEPTION_ORIGIN_INTERNAL
    un code de votre projetExternalCodeC_API_EXCEPTION_ORIGIN_EXTERNAL
    une exception standardstd::exceptionC_API_EXCEPTION_ORIGIN_STD (code C_API_OTHER_EXCEPTION_CODE)
    tout autre objet levé-C_API_EXCEPTION_ORIGIN_UNKNOWN
    une fonction C (utils_fail)-C_API_EXCEPTION_ORIGIN_C

    3. Across the C boundaryÀ travers la frontière C

    An exception must never cross into C code (undefined behavior). Each function of the C API runs its C++ code in a guard:

    1. the call runs in a try;
    2. on success, only utils_exception.exception is set to false (no copy of strings on the fast path);
    3. on an exception, the guard fills the thread local utils_exception (type, code, what, info, file, line, function, module, origin) and the function returns UTILS_KO, NULL or 0.

    The other way, a C callback that fails returns UTILS_KO (or utils_fail(code, info)): the C++ side throws an exception with that info, which goes up like any other and ends in the status of the call that ran the callback. Details: The C API design.

    Une exception ne doit jamais passer dans du code C (comportement indéfini). Chaque fonction de l'API C exécute son code C++ dans une garde :

    1. l'appel tourne dans un try ;
    2. en cas de succès, seul utils_exception.exception est mis à false (aucune copie de chaîne sur le chemin rapide) ;
    3. sur une exception, la garde remplit le utils_exception thread local (type, code, what, info, file, line, function, module, origin) et la fonction renvoie UTILS_KO, NULL ou 0.

    Dans l'autre sens, un callback C qui échoue renvoie UTILS_KO (ou utils_fail(code, info)) : le côté C++ lève une exception avec cette info, qui remonte comme n'importe quelle autre et finit dans le statut de l'appel qui a lancé le callback. Détails : Conception de l'API C.
