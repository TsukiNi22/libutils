    WindowsWindows

    Build libutils and your program for Windows from Linux with MinGW-w64: requirements, packages, the toolchain, your project, the code rules and the tests.Compiler libutils et votre programme pour Windows depuis Linux avec MinGW-w64 : prérequis, paquets, la toolchain, votre projet, les règles de code et les tests.

    Updated 2026-11-26

    Windows x86_64, cross compiled from Linux with MinGW-w64 (toolchain cmake/toolchain/mingw-w64.cmake, packages mingw64-libutils* since v4.1.0). Every class and the Platform calls are implemented with Win32 / Winsock / the CRT, so a program builds for both platforms without change; only a few calls without a Windows equivalent raise a FatalException (UndefinedCall). The design is explained in Platforms.

    Windows x86_64, compilé en croisé depuis Linux avec MinGW-w64 (toolchain cmake/toolchain/mingw-w64.cmake, paquets mingw64-libutils* depuis v4.1.0). Chaque classe et les appels de Platform sont implémentés avec Win32 / Winsock / la CRT, donc un programme se compile pour les deux plateformes sans modification ; seuls quelques appels sans équivalent Windows lèvent une FatalException (UndefinedCall). La conception est expliquée dans Plateformes.

    2. InstallInstallation

    From the packages (after the setup.sh of Installation), installed in the MinGW sysroot:

    sudo dnf install mingw64-libutils       # Fedora: headers, CMake config & optimized library
sudo dnf install mingw64-libutils-db    # Debug library (optional)
sudo apt install mingw64-libutils       # Debian / Ubuntu: OpenSSL for MinGW must be built by hand
    PackageContent
    mingw64-libutilsmingw64-libutils-dev + mingw64-libutils-op
    mingw64-libutils-devHeaders and global CMake configuration (requires mingw64-openssl on Fedora)
    mingw64-libutils-dev-op / -dev-dbCMake configuration of the optimized / debug library
    mingw64-libutils-op / -dblibutils.a / libutils_debug.a for Windows (no asan with MinGW)

    From the sources (any prefix):

    export BUILD_DIR=build-windows
cmake -S . -B $BUILD_DIR -DCMAKE_TOOLCHAIN_FILE=cmake/toolchain/mingw-w64.cmake -DCMAKE_BUILD_TYPE=Optimized
cmake --build $BUILD_DIR --parallel $(nproc)
cmake --install $BUILD_DIR --prefix <windows_prefix>    # include/, lib/libutils.a, lib/cmake/utils/
cmake --build $BUILD_DIR --target package                 # mingw64-libutils-* RPM/DEB (MinGW sysroot)

    cmake/toolchain/mingw-w64.cmake (in the repository, usable by any project):

    4. Your projectVotre projet

    The same CMake code works for Linux and Windows, only the configuration command changes:

    find_package(utils 5.0.0 REQUIRED)
target_link_libraries(${TARGET} PRIVATE utils::utils)   # includes, OpenSSL, ws2_32 on Windows & library
    cmake -S . -B build                                                                           # Linux
cmake -S . -B build-windows -DCMAKE_TOOLCHAIN_FILE=<libutils>/cmake/toolchain/mingw-w64.cmake  # Windows

    Debug links mingw64-libutils-db, anything else mingw64-libutils-op; there is no Asan with MinGW (build in Debug). A missing package stops the configuration with its name.

    Tip. A standalone .exe (without the dll of the MinGW runtime next to it): if(WIN32) target_link_options(${TARGET} PRIVATE -static-libgcc -static-libstdc++ -static) endif(). OpenSSL stays a dll (libcrypto-3-x64.dll, libssl-3-x64.dll from the sysroot bin/) unless its static libraries are installed.

    Le même code CMake fonctionne pour Linux et Windows, seule la commande de configuration change :

    find_package(utils 5.0.0 REQUIRED)
target_link_libraries(${TARGET} PRIVATE utils::utils)   # includes, OpenSSL, ws2_32 on Windows & library
    cmake -S . -B build                                                                           # Linux
cmake -S . -B build-windows -DCMAKE_TOOLCHAIN_FILE=<libutils>/cmake/toolchain/mingw-w64.cmake  # Windows

    Debug lie mingw64-libutils-db, tout le reste mingw64-libutils-op ; il n'y a pas d'Asan avec MinGW (compilez en Debug). Un paquet manquant arrête la configuration avec son nom.

    Astuce. Un .exe autonome (sans la dll du runtime MinGW à côté) : if(WIN32) target_link_options(${TARGET} PRIVATE -static-libgcc -static-libstdc++ -static) endif(). OpenSSL reste une dll (libcrypto-3-x64.dll, libssl-3-x64.dll depuis le bin/ du sysroot) sauf si ses bibliothèques statiques sont installées.

    5. CodeCode

    RuleWhy
    Include <windows.h> before <utils/utils.hpp> (or define WIN32_LEAN_AND_MEAN)The complete <windows.h> declares a member named _unused, a libutils attribute macro
    Call utils::iomanip::enable_ansi() once at the startEnables the virtual terminal mode of the console (colors, cursor); returns true on Unix
    Use utils::platform:: for the system callsSame names and contract as POSIX (-1 and errno), see Platform
    Test the platform with UTILS_WINDOWS / UTILS_UNIXDefined by utils/platform/Platform.hpp (always included), UTILS_PLATFORM = "windows" / "unix"
    The Winsock structures (sockaddr_in, addrinfo, pollfd...)Come from <winsock2.h> / <ws2tcpip.h>, included by the program (not by libutils)

    Different behaviors on Windows (details in Platform, Encapsulation, Cli):

    • Poll, Client and Server only handle sockets (a pipe → EPoll error), EPOLLET is refused (level triggered only);
    • a Process has no signal (Status::sig = 0, killed = exit code 137), only the fds 0, 1, 2 are given to a child;
    • a SharedMemory is destroyed with its last handle (no shm_unlink persistence);
    • Ctrl+Z is a char for the Cli (no SIGTSTP).

    The C API works the same on Windows (the C structures of the POSIX calls come from utils/platform/Types.h).

    RèglePourquoi
    Inclure <windows.h> avant <utils/utils.hpp> (ou définir WIN32_LEAN_AND_MEAN)Le <windows.h> complet déclare un membre nommé _unused, une macro d'attribut de libutils
    Appeler utils::iomanip::enable_ansi() une fois au démarrageActive le mode terminal virtuel de la console (couleurs, curseur) ; renvoie true sous Unix
    Utiliser utils::platform:: pour les appels systèmeMêmes noms et même contrat que POSIX (-1 et errno), voir Platform
    Tester la plateforme avec UTILS_WINDOWS / UTILS_UNIXDéfinis par utils/platform/Platform.hpp (toujours inclus), UTILS_PLATFORM = "windows" / "unix"
    Les structures Winsock (sockaddr_in, addrinfo, pollfd...)Viennent de <winsock2.h> / <ws2tcpip.h>, inclus par le programme (pas par libutils)

    Comportements différents sous Windows (détails dans Platform, Encapsulation, Cli) :

    • Poll, Client et Server ne gèrent que des sockets (un pipe → erreur EPoll), EPOLLET est refusé (level triggered uniquement) ;
    • un Process n'a pas de signal (Status::sig = 0, tué = code de sortie 137), seuls les fds 0, 1, 2 sont transmis à un enfant ;
    • une SharedMemory est détruite avec son dernier handle (pas de persistance shm_unlink) ;
    • Ctrl+Z est un caractère pour la Cli (pas de SIGTSTP).

    L'API C fonctionne pareil sous Windows (les structures C des appels POSIX viennent de utils/platform/Types.h).

    6. TestsTests

    cmake -S . -B build-windows -DCMAKE_TOOLCHAIN_FILE=cmake/toolchain/mingw-w64.cmake -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTS=ON
cmake --build build-windows --parallel $(nproc)     # unit_tests.exe at the root of the repository
ctest --test-dir build-windows --output-on-failure --parallel $(nproc)
    • GoogleTest: the one built for MinGW in the sysroot (find_package(GTest CONFIG), ex: the mingw64-unit-tests image), else downloaded and built from the sources (FetchContent).
    • ctest runs unit_tests.exe with wine; the tests are listed when ctest starts (DISCOVERY_MODE PRE_TEST), and the first start of wine creates its prefix (~/.wine), which can take a few minutes.
    • tests/platform/Platform.cpp runs on both platforms, tests/platform/Windows.cpp only on Windows.
    cmake -S . -B build-windows -DCMAKE_TOOLCHAIN_FILE=cmake/toolchain/mingw-w64.cmake -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTS=ON
cmake --build build-windows --parallel $(nproc)     # unit_tests.exe at the root of the repository
ctest --test-dir build-windows --output-on-failure --parallel $(nproc)
    • GoogleTest : celui compilé pour MinGW dans le sysroot (find_package(GTest CONFIG), ex : l'image mingw64-unit-tests), sinon téléchargé et compilé depuis les sources (FetchContent).
    • ctest lance unit_tests.exe avec wine ; les tests sont listés au démarrage de ctest (DISCOVERY_MODE PRE_TEST), et le premier démarrage de wine crée son préfixe (~/.wine), ce qui peut prendre quelques minutes.
    • tests/platform/Platform.cpp tourne sur les deux plateformes, tests/platform/Windows.cpp uniquement sous Windows.

    7. ExampleExemple

    #define _Platform
#define _Network
#include <utils/utils.hpp>
#include <iostream>

int main(void)
{
    std::cout << utils::version << " " << UTILS_PLATFORM          // "v5.0.0 windows"
        << " " << utils::network::resolve_hostname("localhost")   // "127.0.0.1" (Winsock)
        << std::endl;
    return 0;
}
